# git-hotspots scoring explanation

## Purpose

Hotspots are local Git-history investigation prompts. They point to files
that changed often or recently, carried churn, or repeatedly changed with
other files in the selected evidence universe.

## Score components

- frequency = change_count * 10
- churn = min((additions + deletions) / 25, 40)
- recency = 20 at the selected HEAD timestamp; otherwise it decays by age
  in days as max(0, 20 - age_days)
- cochange = min(cochange_total * 2, 20)
- total = frequency + churn + recency + cochange

The current score is only this sum of file-level Git-history evidence.

## Confidence

- high: at least 3 changes and no row caveats
- medium: at least 2 changes
- low: anything else

## Caveats

Caveats reduce how much confidence to place in a hotspot prompt. Current
caveat classes include:

- shallow history, where available commits may be incomplete
- partial or promisor history, where available objects may be incomplete
- dirty worktrees, where ranking uses committed history only
- binary or non-text churn that Git cannot count normally
- large commits whose co-change evidence may be capped or caveated
- deleted paths or paths not present at HEAD
- Git-detected file rename lineage and scope-partial lineage

## Scope filters

The --scope flag selects a deterministic evidence universe. During the
alpha, the default --scope project preset expands to these root literal
exclude prefixes, in order: .flow/, .zig-cache/, zig-out/, target/,
node_modules/, dist/, build/, coverage/. Project scope is a convenience
default, not a more correct view than full local Git-history evidence.
Use --scope all for the full local Git-history evidence universe with no
built-in project excludes.

Include and exclude prefixes are literal repo-relative prefixes using '/'
separators. They are not globs, regexes, pathspecs, gitignore rules, or
project configuration.

Filters apply before aggregation, scoring, co-change evidence, and limit.
Excludes win over includes. Scoped reports change the evidence universe, so
compare scoped and unscoped reports with that boundary in mind.

## Rename lineage

Git-detected file renames are folded conservatively when both the old and
new paths are in scope. Accepted old-path aliases contribute to the
canonical current path row instead of appearing as duplicate ranked rows,
and --inspect may resolve an accepted alias to that canonical row.

Lineage is limited to local Git file rename edges. It is not symbol or
function lineage, semantic ownership, bug prediction, quality scoring, or
developer ranking.

## Inspect symbols

The --symbols flag is opt-in and valid only with --inspect PATH. It adds
current working-tree Tree-sitter Zig function symbols for the matched
in-scope .zig file. Provider output is current-only enrichment with
freshness, failure, confidence, caveats, and local provenance.

Symbol evidence does not change file score, rank, confidence, co-change
evidence, Git rename lineage, scope, or inclusion/exclusion decisions.
Unsupported or unavailable current files preserve inspected file evidence
and report provider caveats without parser diagnostics or source snippets.

## Limitations and non-claims

Scores are not bug predictions, objective code-quality ratings, maintainer
judgement, developer rankings, productivity analytics, AI/LLM judgement,
semantic ownership, or technical-debt scores.

## Runtime guarantees

This explanation is static. It does not inspect a repository, run Git
analysis, contact remotes, use providers, use cache, require network
access, upload source, or emit telemetry.
